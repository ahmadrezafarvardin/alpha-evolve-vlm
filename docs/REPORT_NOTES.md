## Setup section

- **Mutation LLM and privacy (draft line):** "Mutations were generated by Gemini 3.1 Flash-Lite (Preview), with 15 %
  of calls sent to Gemini 3 Flash (Preview), accessed through ArvanCloud's OpenAI-compatible gateway. Each mutation
  prompt contains the full candidate program and evaluation feedback from the evolution split; it is therefore
  processed by both the gateway operator and Google. No benchmark answers from the held-out splits are ever included."
- **Hardware:** RTX 3090 24 GB (all reported speeds); the initial baseline also on a T4 (FP16), kept as history.
- **Greedy decoding** everywhere (`do_sample=False`), enforced statically for every evolved candidate.

## Evolution system design (core section)

The strongest argument that this is a *designed* system, not a re-implementation: map each AlphaEvolve component,
state every deviation with its reason, and present the extensions as contributions (the README grades "how well you
design and extend" the components).

| AlphaEvolve component | This system (`alphaevolve/`) |
|---|---|
| Program database | Islands (3 Instruct, 2 Thinking) with ring migration; per-island MAP-Elites grid over time/query × quant accuracy; parent = one of the island's top-k (70 %) or a random elite (30 %) (`database.py`) |
| Prompt sampler | Parent code + scores by question category, failure examples from `evo` only, inspirations as diffs against the parent, stochastic directions / change size / number of failures; Thinking prompts lead with bounding the reasoning (`prompt.py`) |
| LLM mutation | SEARCH/REPLACE diffs inside the EVOLVE block, full rewrite as fallback; ensemble 85 % Gemini 3.1 Flash-Lite, 15 % Gemini 3 Flash, drawn per call (`diff.py`, `llm.py`) |
| Evaluation cascade | Static checks → 8 → 64 → 400 evo queries (Thinking 4 → 32 → 128), noise-aware promotion rule (`evaluator.py`, `checks.py`) |
| Evolution loop | Generation loop, atomic checkpoint per generation, push to `evo/<run_id>`, exact resume (`loop.py`) |

**Deviations from the paper, with reasons:**
1. Synchronous generations, not an asynchronous pipeline: one GPU (no parallel evaluation anyway); synchronous
   generations make resume exactly reproducible (same parents, cached LLM calls).
2. No meta-prompt evolution: directions are a fixed, hand-written list sampled stochastically; a second evolving
   database is not worth it at this scale.
3. Scale: tens of children instead of thousands; GPU time per evaluation (3.5 min Instruct, ~70 min Thinking) is the
   binding constraint.
4. Cascade stages are growing slices of the same benchmark (plus static checks), not increasingly hard tests; the
   promotion margin accounts for the sampling noise of small slices.
5. Mutation LLMs: Flash-Lite + Flash instead of Flash + Pro (cost, gateway availability).
6. No LLM-generated feedback scores; feedback is measured failures from `evo`.
7. Fitness: accuracy, with time as a MAP-Elites feature and a noise-aware tie-breaker, instead of a multi-metric set.

**Extensions (original contributions):**
- **Near-duplicate filter:** a child whose edit (set of changed lines, comments/layout ignored) matches a sibling's
  with Jaccard ≥ 0.8 is rejected before any GPU time; siblings only, so crossover is never blocked. Motivated by the
  pilot (2 of 5 children made the same image-caching edit); fired in the first generation of the full run.
- **Noise-aware selection:** timing noise (~7 %) never decides elites or best pointers (>10 % faster required on
  equal accuracy); the promotion rule has a margin for the ~±6-point noise of 64 queries (Thinking: margin 0 plus
  the speed rule, to bound GPU cost).
- **Rule checks (stage 0):** AST-level enforcement of greedy decoding, the allowed model, and no access to gold data
  or the evaluator, so evolution cannot cheat; plus evo-only feedback in prompts.
- **Robust long runs:** pause/resume on API failure (retry vs. pause classification, spurious-401 confirmation), a
  manual PAUSE file, exact resume from cached LLM calls and stage scores, push timeout, recovery from the run branch.
- **Inspirations as diffs:** −56 % prompt tokens with the same information.
- **"Already tried" memory:** each prompt lists the edits already proposed from the same parent with their outcome
  (same accuracy / ±x % / stopped / a repeat / could not be applied); added after the first full-run attempt
  repeated two ideas 4× and 3×. Uses no random draws, so resume stays exact.

**Known limitations (state honestly):**
- **Neutral edits still cost a full evaluation (Instruct):** with the 3-point promotion margin, an edit that changes
  no answer (e.g. post-processing that never triggers) passes the 64-query check and pays for the 400-query stage
  (~2.5 min). In generation 1 of the first attempt, 3 of 4 evaluated children were neutral. Kept for consistency
  within the run; the Thinking run uses margin 0 (with the speed rule) because a full stage costs ~1 h there.
- **Thinking evolution is tiny** (2 generations × 3 children) because one full evaluation costs ~70 min.
- **Mutation LLM quirks:** Gemini 3 Flash (Preview) thinks by default and needed `reasoning_effort` low; the
  gateway once returned a spurious 401.

## Method / evaluation design

- Splits disjoint by figure: dev 128 (design), evo 400 (evolution fitness), holdout 800 (final comparison only),
  reserve 2,672 (untouched data; uses logged). reserve[:400] became a partial tuning set during manual Instruct work;
  reserve[400:800] was used once, to validate routing.
- Evaluation cascade 8 → 64 → 400 with a promotion rule that allows for the ~±6-point noise of 64 queries.
- Timing noise ~7 % on the same GPU; differences under ~10 % are not claimed; selection ignores them.

## Results and analysis

- **Negative result:** more extraction rules did not help (step 2a: dev +1, reserve +0); extraction saturates.
- **Answer-only prompt:** same accuracy as verbose answers + extraction at 5.4× the speed (step 2b).
- **Precision/recall trade-off** of the "Not Applicable" prompt (step 2c): recall 20 → 44 %, precision 100 → 73 %,
  net +4 points on reserve; false abstentions cluster by question type.
- **Thinking second-guessing:** cutting reasoning before the 4th "Wait" keeps or raises accuracy with ~60 % fewer
  reasoning tokens (intervention, `analysis/wait_probe_*.json`); manual_thinking was deliberately left unchanged,
  the finding motivates a mutation direction for Thinking evolution.
- **Routing** (number-reading/counting → Thinking, rest → Instruct; `route_quant.py`), validated on reserve queries
  400–800 (untouched until then): **67.8 % vs. 58.8 %** for Instruct alone on the same queries (+9.0 points).
  - **McNemar:** 49 answers right only when routed, 13 right only with Instruct; χ² ≈ 21, **p < 0.001**.
  - **Where:** all of the gain is on the 164 routed questions (75 → 111 correct); the other 236 answers are identical.
    Per question type (Instruct → routed): **counting labeled ticks +10** (2 → 12 / 21), **colorbar maximum +9**
    (5 → 14 / 36, mostly correct "Not Applicable"), number of lines +3, legend label count +5, tick differences
    +6 / +2, colorbar range +2, **number of subplots −1** (7 → 6 / 7).
  - **Cost: 28× slower** (10.7 vs. 0.38 s/query; 98 % of the time is the routed questions at 25.5 s each; 55/164
    exhaust the 1,024-token reasoning budget). **Projection:** if reasoning is bounded as the "Wait" measurement
    suggests (~60 % fewer reasoning tokens), ~4 s/query. Not measured; state as a projection.
  - **Framing:** a *combined* approach (two models in one pipeline). Flag it explicitly; the README allows the
    best_* scripts to use "either model and any approach (manual, evolved, combined, or otherwise)". It is a
    `best_accuracy` candidate, not `best_overall` at this speed.

## Overfitting and generalization (audit, 2026-10-15)

**Holdout is the only split not used for any design decision, and is the report's primary evidence.** Every
other number below is either fitted to the data it was measured on, or a single-use validation.

**Which decisions were made on which split:**

| Split | Used for | Status of its numbers |
|---|---|---|
| `dev` (128, the public official set) | Writing the extraction rules (step 1, 2a) from dev responses; the "Not Applicable" prompt (2c) from dev failures; `max_new_tokens` 64 from dev gold-answer lengths; the Thinking budget probe (dev[:32]); the "Wait" intervention; part of the routing evidence (Thinking vs. Instruct per category) | **Fitted / optimistic** for every manual version |
| `reserve[:400]` | Step 1 extraction replay (first use: honest at that time); then keep/drop decisions for steps 2a–2c; Thinking step 1 on reserve[:128]; the routing design (Thinking clearly better on the quant category there) and the "Wait" intervention | **Partial tuning set:** step 1's 51.7 % was honest when measured; later numbers are optimistic. The 63 % routing estimate was fitted. |
| `reserve[400:800]` | One use: routing validation (67.8 % vs. 58.8 %) | **Honest single-use validation** (no decision made on it before; it decided to keep routing) |
| `evo` (400) | Evolution fitness and selection only (plus a 64-query prompt-format check of `manual_instruct` before the runs) | **Fitted** for every evolved program ("training fitness") |
| `holdout` (800) | Nothing yet; final comparison of all versions only | **The only clean test** |

**Rules derived from inspecting the dataset (not from general intuition alone):**
- Extraction regexes and the superscript → caret rule: written while reading dev responses and gold answers.
- The "Not Applicable" prompt wording (colorbar example): from dev failure clusters (qid 14/15).
- The 64-token answer budget: from dev gold-answer lengths.
- The routing phrases: copied from CharXiv's own question templates (`charxiv/src/constants.py`), i.e. the
  benchmark's source code, not its answers. *Which* types to route (CharXiv's own "quant" grading category, qids
  8, 9, 10, 12, 14, 15, 17, 19) was chosen from performance on reserve[:128] and dev.
- The mutation directions (per-question-type NA guidance, counting, "n by m" layout format) are hand-written from
  the dev/reserve error analyses; evolution itself sees only evo results.
- Hyper-parameters of the evolution system (near-duplicate threshold 0.8, promotion margins, timing-noise band) were
  set from the pilot and timing measurements on evo / dev.

**The routing rule, exactly:** `route_quant.needs_reasoning` lowercases the question's first line and checks seven
fixed substrings (e.g. "how many lines are there", "total number of explicitly labeled ticks across all axes"); no
regex, no learning. A match goes to `manual_thinking` (step 1), anything else to `manual_instruct` (step 2c).
- **Not an evolved program:** `route_quant.py` was never a mutation target (no reference in `alphaevolve/` or the
  evolve scripts). It is a **manual design**; its holdout number tests the author's routing choice, not evolution.
- **Caveat on "0 misrouted":** the check (0 of 4,000 distinct validation questions) was computed over the same
  CharXiv validation data whose templates the phrases were copied from, so it only verifies that the string
  matching reproduces the template → question-type mapping; it is not evidence of generalization. It holds for any
  question generated from the same templates (the hidden test set uses the same descriptive templates); a
  differently phrased question would fall through to Instruct, the cheaper default. An earlier report of "0 of
  7,872" double-counted: `load_charxiv_data(None, "dev")` returns all 4,000 validation questions, not the 128 dev ones.

**Honest vs. fitted numbers to report:**
- Honest: step 1 extraction on reserve[:400] (51.7 %, measured before reserve was used for decisions); routing on
  reserve[400:800] (67.8 % vs. 58.8 %); every holdout number.
- Fitted / optimistic: all dev numbers of manual versions; reserve[:400] numbers of steps 2a–2c; all evo numbers of
  evolved programs; the 63 % routing estimate (reserve[:128]).
- The dev − reserve gap of manual Instruct grew from 4.5 to 10.4 points over steps 1 → 2c: a measured sign of
  fitting to dev, reported as such.

## Instruct evolution: analysis points

- **Framing (required):** "+7.75 points" (54.75 → 62.50 %) is **evo fitness**: evolution improved the seed by 7.75
  points on its training split; holdout shows whether that transfers. Never present an evo number as generalization.
- **Two-lineage convergence:** seed → g006_c04 → g007_c01 → g009_c01 → g010_c01 (62.50 %) and seed → g001_c02 →
  g004_c02 → g007_c05 → g008_c02 (62.25 %) reached the same level independently; evidence the improvement is a real
  property of the edits rather than one lucky child (still on evo; holdout is the test).
- **Cascade efficiency, measured honestly** (GPU wall time vs. evaluating each of the 62 children that had a
  program once on all 400 queries, 155 s each = 160 min): actual 144 min, **net saving 16 min (10 %)**.
  - Static filters: 11 programs never evaluated (6 duplicates, 4 near-duplicates, 1 rule violation): **+28 min**.
  - Early stops: 13 children cost 10 min instead of 34 at full: **+24 min**.
  - Overhead: the 38 children that reached the full stage also paid smoke + subset (57 s each): **−36 min**.
  - (10 invalid edits never touched the GPU, but they are not a saving: no program existed.)
  - **Reading:** for Instruct the filters are the real win; staged evaluation roughly breaks even because a full
    evaluation is cheap (2.6 min) and 75 % of evaluated children passed. Staged evaluation pays off when a full
    evaluation is expensive (Thinking: ~54 min saved per early stop) or the pass rate is low. Report it this way,
    not as a blanket win.

## Thinking evolution: analysis points

- **Result, framed honestly:** `g001_c00` (`_THINK_BUDGET` 1024 → 512, plus comma spacing) runs **−30 % time at the
  same accuracy** on evo[:128] (19.9 → 14.0 s/query; 71.9 → 74.2 %, +3 answers, within ±4 points: not a gain).
- **Evolution found the simplest mutation, not the best one (negative result):** the "Wait"-stopping intervention
  (cut before the 4th "Wait") was measured to cut ~60 % of reasoning tokens with accuracy kept or raised, and the
  prompt suggested it first; evolution instead chose the lower budget, a one-number edit. A hand-built Wait-stopping
  version would likely beat what evolution found. LLM-guided evolution prefers mutations that are easy to express in
  code over the most effective ones, at least at this scale (6 children) and with small mutation models.
- **Diversity failure (limitation):** 4 of 6 Thinking children were byte-identical ("budget 512 + comma spacing"),
  although every one of their prompts carried the "already tried" list. The exact-duplicate check meant no GPU was
  wasted, but only 2 distinct children were evaluated. The ensemble (85 % Flash-Lite, 15 % Flash) is only a partial
  mitigation: here both models proposed the same edit. Possible remedies (not tried): higher temperature for
  repeated parents, rejecting a reply whose idea matches a tried one before applying it, a stronger model.

## Holdout results (primary evidence, 800 queries)

- Table: RESULTS.md, entry 2026-10-16. Accuracy / s/query: baseline 25.9 / 2.61; manual_instruct 56.0 / 0.41;
  evolved_instruct 62.0 / 0.46; manual_thinking 64.8 / 28.6; evolved_thinking 67.0 / 19.3; routing (manual) 61.6 /
  14.5; routing (evolved) 63.4 / 8.0. Routing numbers are composed; a direct run on 32 queries matched 32/32.
- **Headline finding, routing reversal:** "A design validated against the wrong baseline (Instruct alone) failed
  against the right one (Thinking alone)." Routing beat Instruct alone on reserve[400:800] (+9.0, p < 0.001) and on
  holdout (+5.6, p < 1e-5), but Thinking alone is better still on holdout (64.8 vs. 61.6 %), because Thinking is
  also better on ocr (+19) and layout (+5); the routing design came from reserve[:128], where it was not.
- **Instruct evolution generalizes:** +7.75 points on evo (training) → **+6.0 on holdout** (56.0 → 62.0 %, McNemar
  p = 0.0003); almost all of it on quant (132 → 174 of 326).
- **Thinking evolution holds up:** **−33 % time** (28.6 → 19.3 s/query) and **+2.2 points, p = 0.01** on 800
  queries (on evo[:128] the accuracy change was within noise; holdout has the power to see it).
- **Pre-registration issue (state it):** routing was the pre-registered `best_accuracy` candidate. After holdout
  contradicted it, the selection of `best_accuracy` (and `best_speed`) moved to a fresh slice, reserve queries
  800–1000, so that holdout stays the clean test; `best_overall` (evolved_instruct) was decided on holdout, with a
  margin large enough that the selection bias is negligible.

## Final selections (reserve queries 800–1000; RESULTS.md 2026-10-16)

- **Routing composition verified:** a direct `route_quant` run on holdout[:32] gave 32/32 answers identical to the
  composition from the Instruct and Thinking runs (19/32 correct in both), time within 1 % (368 vs. 372 s).
- **Manual Thinking kept on the selection slice:** without it, routing with the manual models would not be
  measurable there; completeness of the comparison was preferred over 1.5 h of GPU time.
- **Selection slice results** (200 queries): evolved_thinking 72.0 % (14.4 s/q), manual_thinking 71.0 % (21.7),
  routing manual 70.0 % (9.9), routing evolved 69.5 % (6.5), evolved_instruct 67.0 % (0.45), manual_instruct
  63.0 % (0.44). Top differences not significant on 200 queries; ordering consistent with holdout.
- **best_accuracy = evolved_thinking** (holdout 67.0 %, clean); **best_speed = manual_instruct** (strict rule; the
  speed difference to evolved_instruct is within noise and costs 4–6 points of accuracy: say so);
  **best_overall = evolved_instruct** (decided on holdout; large margin).
- Narrative: the most accurate system is the Thinking model with an evolved (halved) reasoning budget; the best
  accuracy/speed trade-off is the evolved Instruct model; routing sits between them and lost its pre-registered role.
